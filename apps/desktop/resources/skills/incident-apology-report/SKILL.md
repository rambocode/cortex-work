# 故障/异常情况说明致歉报告生成技能

本技能用于将一段（可能很随意、很简略的）故障描述，转化为一份可以直接发给客户的、正式诚恳的《故障/异常情况说明及致歉报告》Word 文档。

## 先确定业务语境

本技能不预设你所在公司的行业。动笔前按下面的顺序确定语境，**确定不了就直接问用户**，不要凭空假设：

1. 工作区 / 会话上下文里已有的公司与业务信息（项目文档、既往会话、用户记忆）优先。
2. 取不到就从用户的故障描述里推断（提到"探头/库房/冷链"多半是监测类服务，提到"订单/支付"多半是交易类服务）。
3. 都推断不出来，就按中性的「SaaS 服务商 → 企业客户」框架写，并在交付时说明你采用的假设。

**不论哪种语境，有一条通用洞察必须贯穿全文：客户在意的不是我们的服务器发生了什么，而是"我的业务、我的数据、我的合规记录有没有事"。** 所以永远先给客户视角的影响与数据安全结论，再讲技术原因。

> 举例（说明这条洞察怎么落地，不是让你套用这个行业）：如果你的产品是温湿度监控 SaaS，客户多为医药、冷链物流、仓储、食品、实验室，他们要用平台数据应对 GSP/GMP 合规审计——那么一次平台中断对他们就不是"不方便"，而可能直接影响货品安全与审计记录的完整性，报告就必须正面回答"故障时段的数据有没有丢、能不能补、审计怎么交代"。换成别的行业（如支付、客服、协同办公），同样要找到"客户真正怕什么"，并把它放在报告最前面。

## 工作流程

### 第 1 步：从用户描述中提取信息

通读用户的故障描述，提取以下要素。用户的描述往往不完整，先把能推断的推断出来：

- 故障现象（平台无法访问？数据未上传？报警未发出？误报警？）
- 故障时间段（开始、恢复、总时长）
- 影响范围（全部客户还是部分？哪些功能受影响？）
- 故障原因（如果用户说了）
- 处理过程（如果用户说了）
- 数据是否缺失、是否可补录

### 第 2 步：补齐关键信息

生成报告前，有些信息**编不得、猜不得**，缺了必须要向用户确认（用 AskUserQuestion/askquestion/其他 可用的询问用户的tool和用户确认；无人值守时用明显的占位符并在交付时说明）：

1. **故障时间段**——如果用户完全没提时间，需要问；报告里的时间必须来自用户，不能虚构。
2. **收件对象**——是发给全体客户的通告，还是发给某个具体客户的报告？影响称呼和措辞。
3. **落款主体与联系方式**——公司全称、客服热线/邮箱。这是一封正式对外函件的署名，编不得。上下文里有就直接用（工作区文档、用户记忆、既往报告），没有就问。

以下信息**可以合理撰写而无需询问**：原因分析的措辞、处理过程的表述、改进措施（可根据故障类型给出行业常规的合理措施，如增加冗余、完善监控、优化发布流程等）、致歉与承诺的内容。这些属于"把用户给的事实写得体面"，不属于编造事实。注意分寸：改进措施可以合理泛化，但**不要虚构具体赔偿金额、具体补偿方案、具体到期日的承诺**——除非用户明确给出。

### 第 3 步：匹配常见故障场景，选用模板

在线服务平台（尤其是带数据采集与报警的监测类服务）的日常故障绝大多数落在五类常见场景里。`assets/templates/` 下为每类场景准备了**完整的报告模板**（content.json 骨架，含固定措辞和 {{槽位}}）。用模板的目的是**同类问题的报告保持一致**——同一类故障，不管谁来生成、生成多少次，客户收到的报告结构和措辞都是一样的，只有事实不同。

| 场景 | 判断特征 | 模板文件 |
|------|----------|----------|
| 平台服务中断 | 网页/App 无法访问，平台整体不可用 | `platform-outage.json` |
| 数据上传中断（可补录） | 部分设备数据没上传，但本地有存储、最终无缺失 | `data-gap-recoverable.json` |
| 数据缺失（无法补录） | 某时段数据永久丢失，补不回来 | `data-loss-unrecoverable.json` |
| 报警误报 | 误发/重复发报警，实际业务指标正常（默认简洁版） | `false-alarm.json` |
| 报警漏发/延迟 | 指标可能超限但报警没发出去或迟到 | `missed-alarm.json` |

模板里的行业相关表述统一做成了 {{槽位}}（如 `{{平台名称}}`、`{{监测对象}}`），按开头「先确定业务语境」一节的结论填写即可。

选择方式：

- 从用户描述能明确判断场景的，直接选用对应模板，并在回复中告知用户用了哪个场景模板。
- 判断不确定、或一次事件横跨多个场景的（如平台中断+部分数据缺失），用 AskUserQuestion 让用户从上表中选择（选项就用上表的场景名）；无人值守时选影响最重的场景为主模板，从其他模板借用所缺章节。
- 五类都不沾边的（如安全事件、计费错误），不套模板，按 `references/writing-guide.md` 的章节结构自由撰写。

### 第 4 步：填充模板 / 撰写内容

**用模板时**：读取对应模板文件，按其 `_usage` 说明操作——{{槽位}} 填入第 1、2 步收集的事实；〔可选:…〕标记的段落/条目按实际情况保留（去掉标记）或整段删除；**其余模板文字保持原样，不要改写**——改写会破坏同类报告的一致性，这正是模板要防止的。模板没覆盖、但用户明确要求写进去的内容，可以增补段落，措辞风格与模板保持一致。

**签名与联系方式必须是真实值，不能留占位符**：`signature.company` / `signature.extra` 取自第 2 步确认的落款主体与联系方式。交付件里**绝不能出现** `【公司名称】`、`【客服热线】`、`{{联系方式}}` 这类占位符——一封签着 `【公司名称】` 的致歉函发出去比不发更糟。正文中的联系方式槽位（如 `{{联系方式}}`、`{{客服热线×××／您的专属客户经理}}`）用同一份信息填。

只有在**无人值守、确实问不到**时才允许保留占位符，此时必须在交付说明里逐条列出「以下占位符需你替换后再发出」。若你所在团队每次都用同一套落款，把它写进工作区文档或用户记忆，本技能下次就能直接取用、无需再问。

`signature.date` 使用本次报告落款日期，必须来自用户描述或确认。

**自由撰写时**（无匹配模板）：写作原则详见 `references/writing-guide.md`（**动笔前先读它**，里面有语气规范、常用措辞、各章节写法和敏感表述红线）。核心几条：

- 语气：正式、诚恳、担责。不推诿（不说"由于第三方云服务商问题"就完事，即使真是第三方问题，也要表达"我们对服务商的管理和容灾预案负有责任"）。
- 立场：站在客户视角先讲影响和数据安全结论，再讲技术原因。
- 克制：不夸大也不淡化。"给您带来了不便"这种轻飘飘的话不适合数据缺失类严重故障，要用"给贵司的质量管理工作带来了影响，我们深表歉意"这类分量相称的表达。
- 数据缺失场景：必须写清缺失时段、是否可补录/如何补录、对客户合规记录的影响及应对（如出具本情况说明供客户存档备查，作为审计时的偏差说明附件）。
- 合规敏感客户：加入"合规性说明"章节，评估本次事件对客户业务记录完整性的影响，并明确本报告可作为其质量/合规体系中的偏差处理支持文件。**是否合规敏感取决于客户所处行业**——医药（GSP/GMP）、冷链验证、食品、实验室、金融等属典型；判断不了就问用户，不要默认加或默认不加。

### 第 5 步：生成 Word 文档

用打包好的脚本生成，不要手写 python-docx 代码。**脚本路径必须写成绝对路径或以本技能目录为前缀**——你的工作目录是用户的工作区，不是本技能目录，写相对路径会找不到文件：

```bash
python3 <本技能目录>/scripts/generate_report.py content.json -o 故障情况说明及致歉报告.docx
```

填好的模板（或自由撰写组织成的 JSON，字段说明见 `references/content-schema.md`）保存为 `content.json`——注意删掉模板里的 `_scenario`、`_usage` 说明字段，并确认没有残留的 {{槽位}}、〔可选〕标记或联系方式占位符。脚本会负责公文排版：标题、编号、称呼、自动编号的章节、处理过程时间线表格、落款、日期，中文字体与行距均已按正式公文习惯设置。

**环境缺 `python-docx` 时脚本会自动降级**：输出同名 `.md` 而非 `.docx`，退出码仍为 0，并在 stdout 打印一行提示。此时把降级提示**原样转达给用户**（含 `pip3 install python-docx` 这条修复命令），别假装交付了 Word 文档。若连 `python3` 都没有，就直接把 `content.json` 的内容按报告结构写成 Markdown 交付，并说明未能生成 Word 版本的原因。

生成后向用户交付：明确给出文件的完整路径；若当前环境有文件发送工具（如 `SendUserFile`），用它直接把文件发给用户。附一句话说明；若保留了占位符，逐条列出哪些需要用户替换。

### 第 6 步：自检

交付前核对：

- 报告中的所有**事实**（时间、现象、影响、原因）均来自用户描述或用户确认，没有虚构；
- 时间线前后一致，时长计算正确（跨天要算对）；
- 没有出现赔偿金额、违约金等用户未授权的承诺；
- 落款信息正确：`signature.company` / `signature.extra` 是第 2 步确认过的真实公司名与联系方式；除非无人值守且确实问不到，否则不得残留公司名或联系方式占位符（保留了就必须在交付说明里列出）；
- 全文没有残留本技能自身的行业假设——若业务语境是推断出来的而非用户确认的，在交付时说明你按什么假设写的；
- 标题、称呼与收件对象匹配（发全体客户用"尊敬的客户"，发具体客户用"尊敬的×××公司"）；
- 使用模板时：无残留的 {{槽位}}、〔可选〕标记及 `_scenario`/`_usage` 字段，未擅自改写模板固定措辞。

## 文件说明

- `assets/templates/` — 五类常见故障场景的报告模板（content.json 骨架，含固定措辞与槽位）：`platform-outage.json`、`data-gap-recoverable.json`、`data-loss-unrecoverable.json`、`false-alarm.json`、`missed-alarm.json`。
- `references/writing-guide.md` — 写作指南：语气规范、各章节写法、措辞库、红线。自由撰写及增补模板外内容前必读。
- `references/content-schema.md` — content.json 的字段说明与完整示例。
- `scripts/generate_report.py` — Word 文档生成脚本（python-docx；缺该库时自动降级输出 Markdown）。
