# 写作指南

## 总体语气

正式公文体 + 诚恳担责。想象收件人是客户的质量负责人或设备负责人：他要拿这份文件向他的领导、他的审计员交代。所以这份报告既是道歉，也是**替客户完成向上解释工作的材料**——写得越清楚、越有担当，客户越省事，越会觉得这家供应商靠谱。

三个"不要"：

1. **不要推诿。** 即使根因在第三方（云服务商、运营商、上游硬件），也要落到自己的责任上："对服务商的依赖管理与容灾预案不足，我们负有责任。"
2. **不要轻描淡写。** "带来不便，敬请谅解"只适合几分钟的小抖动。数据缺失、报警失效这类可能影响客户业务安全和合规的故障，要用与之相称的分量："本次事件对贵司的{{监测/业务}}记录完整性造成了影响，我们对此深表歉意，并向贵司郑重致歉。"
3. **不要过度渲染。** 不用"万分""无比沉痛"这类夸张词，也不要连篇累牍地道歉。诚恳来自具体：讲清楚发生了什么、我们做了什么、以后怎么防止，比十句"对不起"都有效。

## 标准全套章节结构与写法

报告章节按以下顺序（脚本会自动编号"一、二、三……"）：

### 事件概述
两三句话：什么时间、什么系统/功能、发生了什么、什么时间恢复、总时长。开门见山，不绕弯子。

### 影响范围
客户最关心的部分，写具体：受影响的功能（实时监控/历史数据/报警短信/App 推送……）、受影响的时间段、受影响的客户/设备范围。**关键结论前置**：数据是否缺失、报警是否漏发，要在这一节明确给出结论，不能让客户自己去猜。若设备端有本地存储、数据可补录，这是最能安抚客户的信息，务必写明。

### 原因分析
用客户能懂的语言解释根因，技术术语点到为止（"数据库主节点磁盘故障导致服务切换耗时过长"可以，不必展开讲 raft 选主细节）。原因未完全查明时如实写"初步分析为……，详细根因仍在进一步排查中，查明后我们将补充通报"，不要编一个确定的原因。

### 处理过程
时间线形式（脚本渲染为表格），每行"时间 + 动作"。从故障发现（或首次报警）写到确认恢复。时间线传递的信息是：我们发现得快、响应得快、有章法。

### 数据补偿说明（涉及数据缺失时加入）
写清：缺失/延迟的时段与范围；能否补录（设备本地缓存回传、人工补录通道）；补录的时间安排；无法补录的部分如何处理——本报告可作为该时段数据缺失的正式情况说明，供客户存档备查。

### 合规性说明（客户处于合规敏感行业时加入）
典型如医药（GSP/GMP）、冷链验证、食品、实验室、金融——判断不了就问用户，别默认加也别默认略。写法：评估本次事件对客户业务记录完整性、连续性的影响；说明本报告可作为客户质量/合规管理体系中偏差处理、审计答复的支持性文件；如客户需要，可提供加盖公章的正式版本及补充技术说明。

### 改进措施
3~5 条，具体、可信。每条尽量"措施 + 目的"，如"增加数据库跨可用区冗余部署，避免单节点故障导致服务不可用"。可根据故障类型合理撰写行业常规措施，但**不承诺具体完成日期**，除非用户提供。

### 致歉与承诺
收尾段：再次致歉 + 表达对客户业务重要性的理解 + 承诺 + 客服联系方式（如有）。示例见下方措辞库。

## 简洁版结构

事件说明（概述+影响合并）→ 原因 → 致歉与承诺。全文控制在一页内，不用时间线表格。

## 措辞库

开头称呼后的首段：
- "首先，对本次系统故障给贵司业务带来的影响，我们深表歉意。现将有关情况说明如下："
- 发全体客户："现就 ×月×日平台服务异常情况向各位客户说明如下，并向受影响的客户致以诚挚歉意。"

数据安全结论（有本地缓存时）：
- "故障期间，各{{终端／采集设备}}本地数据记录功能正常，{{监测}}数据已完整保存于设备端；平台恢复后数据已自动回传补齐，未造成数据缺失。"

数据缺失时：
- "经核查，×时×分至×时×分期间部分测点的平台端数据存在缺失，具体范围见下文。对由此给贵司数据记录完整性造成的影响，我们深表歉意。"

结尾承诺：
- "{{数据／服务}}的连续、准确、可追溯，是贵司对我们的信任所在，也是我们服务的根本。我们将以本次事件为鉴，切实落实上述改进措施，防止类似问题再次发生。"
- "如贵司对本次事件有任何疑问，或需要我们提供进一步的技术说明与配合，请随时联系客服热线 ×××（或您的专属客户经理），我们将第一时间响应。"（×××须替换为真实热线，不得原样发出）

## 红线（务必遵守）

- 时间、故障现象、影响范围、原因等**事实性内容**只能来自用户提供的信息；用户没说的事实不要编。原因不明就写"正在排查"。
- 不写具体赔偿金额、免费延期、违约金等实质性补偿承诺，除非用户明确授权。可以写"如贵司因本次事件产生相关疑问或需求，欢迎与我们协商"。
- 不点名指责第三方厂商（可以说"云服务基础设施故障"，不要写具体厂商名并把责任推给它）。
- 不透露其他客户的名称或信息。
- 落款公司与联系方式不视为临时待补事实，默认使用 `references/content-schema.md` 中的 `signature.company` 和 `signature.extra`；只有用户明确给出其它公司名、热线或邮箱时才覆盖。落款日期必须来自用户描述或确认。
