# 合同审查与报告

## 总体要求

以合同文本和可核验材料为证据，不把 OCR 推断当成确定事实。先确定审查视角：

- 用户明确指定甲方或乙方时，以该方利益为主，同时提示双方共同风险。
- 未指定视角时，默认输出双方中性风险报告，并在开头询问或建议选择谈判立场；若用户要求直接交付，分别给出甲方/乙方最关键风险。
- 合同审查不是律师正式意见；涉及诉讼、重大金额、数据合规、劳动、知识产权或监管许可时，明确建议专业律师复核。

报告必须区分四类内容：已从合同确认的事实、基于条款的风险判断、需要补证的事项、建议条文。不得编造合同未出现的附件、日期、签章或交付事实。

## 工作流

工作流的每一步是**分析动作**，不是报告章节。第 2、4、5 步的发现统一登记为带编号的风险项（R1、R2…），最终只按"报告结构"一节的固定模板输出——不要把检查步骤逐个映射成"××表"章节。

### 1. 提取合同并建立证据索引

**合同通常是用户直接拖进输入框的附件，不要向用户索要文件路径。** 路径在消息附件的 `files[].path` 里，按下面的顺序取用：

- 有 `extract_document` 工具时（Cortex 桌面端会挂载它）：用它读文本，入参就是附件的 `files[].path`。
- 没有该工具、或用户明确给了路径时：按普通文件读取。
- 两者都没有——即用户只说了"帮我审合同"却没带附件：这时才提示用户把合同拖进输入框，不要凭空猜文件名，更不要编造一个路径去读。

拿到内容后：

1. 确认页数、是否加密、是否有附件、签约主体和用户要求的视角。
2. 文本型 PDF/Word 优先提取文字；扫描件先 OCR，再逐页回看关键页面（首页、金额付款、责任、验收、签章、附件）。
3. OCR 不清的字段标记为"待核验"，不能擅自补全。印章、骑缝章、手写日期、签字与盖章主体是否一致，只能从页面图像确认，不能从文本推断。
4. 建立证据索引：`合同条款/附件/页码 -> 事实 -> 风险`。对缺失附件、空白栏和页面不连续单独列出。

扫描 PDF 可使用 `pdftoppm` 渲染页面和系统 OCR——渲染的输入路径同样是附件的 `files[].path`（`extract_document` 只出文本，出不了页面图像）。脚本和临时文件只放在工作目录，不覆盖原件。

### 2. 形式与数值自检

合同纠纷里相当一部分源于可机械核对的错误，这一步成本低、收益高，必须在实体分析之前完成：

- 大写金额与小写金额一致；含税额 = 不含税额 × (1 + 税率)；税额自洽。
- 付款节点比例合计是否等于 100%；各节点金额 = 比例 × 总额；付款触发条件（发票、验收、上线）是否可能互相死锁。
- 日期链条自洽：签订日期 → 生效条件 → 服务/履行期限 → 交付期限 → 验收期限 → 质保/质保金释放。特别注意不同条款用不同起算点（"签订后 X 日"与固定日期）导致的隐性冲突。
- 主文引用的每个附件是否实际存在于文件中、页码是否连续、编号是否对得上。引用了但不存在的附件是 P0 问题——附件往往就是验收标准和价格清单本身。
- 银行账号、主体全称、签章名称、地址三处以上出现的信息互相一致。

所有不一致记入证据索引（见"报告结构"），不得默认为笔误而忽略。

### 3. 识别合同类型和履约链路

先判断合同是买卖、服务、技术服务、软件开发、承揽、咨询、许可、委托、采购、维保或混合合同。混合合同时拆成：

`需求/资料 → 设计 → 开发/供货 → 测试/上线 → 验收 → 付款 → 质保/维保 → 终止/交接`

按该链路检查每个阶段的责任主体、输入、输出、期限、证据、付款触发条件和失败后果。技术服务或软件开发合同必须特别核对成果权属、既有组件、源代码、第三方组件、接口依赖和变更管理。

**需求边界专项**（技术服务/软件开发/承揽类合同必做，需求条款是此类合同争议的第一来源）：

- 逐条核对需求清单（如 URS）：每条需求能否映射到明确的交付物、验收标准和费用覆盖；映射不上的需求就是隐性义务。
- 摘出所有开放式表述并逐条评估：如"包括但不限于""等""不限于此""配合完善""满足甲方需求"。开放式表述 + 固定总价 + "无须另行支付其他费用"的组合，意味着范围风险全部由供方承担。
- 识别伪装成需求的长期义务：写在需求附件里的年度维护、版本更新、新平台对接、驻场支持等，核对其期限、费用是否与主文一致，是否被总价"免费"覆盖。
- 确认变更管理机制是否存在：无书面变更单机制时，任何口头需求扩张都难以主张加价。

### 4. 内部一致性与缺漏检测

这两项是模板化合同最常见的病灶，单看每个条款都"正常"，放在一起才暴露问题：

- **冲突核查**：对同一事项（响应时间、质保期、交付期限、验收标准、培训义务等）逐项比对主文与附件、附件与附件的约定。若合同声明附件与主文"同等法律效力"却没有文件优先顺序条款，任何冲突都会变成解释权之争，冲突项风险升一级。
- **缺漏检测**：对照该类型合同应有的条款清单（见 [references/review-checklist.md](references/review-checklist.md) 的"条款完备性对照"），逐项标注"有 / 无 / 含糊"。没写的条款比写坏的条款往往风险更大——空白处将适用法定默认规则，要说明默认规则对指定视角是有利还是不利（例如委托开发未约定权属时成果归属的法定规则）。

### 5. 风险扫描与责任对称性分析

按 [references/review-checklist.md](references/review-checklist.md) 的十个维度逐项扫描，并按用户视角改写风险后果。在此基础上做两项专项分析：

- **对称性扫描**：对每一项违约金、赔偿、解除权、扣款权，检查对方是否有对应机制。典型不对称：乙方逾期交付有 30% 违约金，甲方逾期付款却无任何责任；保密违约金只约束一方。发现的不对称按视角评估应争取对等还是保留优势，作为风险项进入风险清单。
- **叠加检查**：违约金、退还已付款、赔偿损失、第三方费用是否可同时主张，有无责任上限。多重责任无上限叠加对承担方是 P0 风险。

每个高风险项写成：`条款位置 + 合同事实 + 可能后果 + 风险等级 + 修改动作 + 建议条文`。风险等级用 `P0/P1/P2`：P0 影响签署、回款、核心交付或重大责任；P1 可能导致履约或争议；P2 为证据、表述或执行优化问题。

### 6. 法律与行业合规核验

法律结论会随法规、司法解释和监管规则变化，凡涉及法律判断先通过互联网检索核实，优先中国人大、国务院、最高人民法院、国家网信部门、市场监管部门等官方来源。只引用与结论直接相关的条款，报告放置可点击来源链接，说明法律适用仍需结合事实。常用核验方向见 [references/clause-library.md](references/clause-library.md)。

通用法律之外，先识别行业场景，再加载行业合规层（见 checklist 的"行业合规映射"）：医药相关系统涉及 GSP 和数据完整性要求，个人信息处理涉及委托处理协议要点，政府采购涉及保证金与程序限制等。行业强制要求写不进合同同样构成风险。

不要用泛泛法律常识替代条款分析；未核实的法律来源标为"需律师核验"。

### 7. 优化建议与谈判优先级

针对每个 P0/P1 风险，优先给出可以直接放入补充协议的条文（条文骨架见 [references/clause-library.md](references/clause-library.md)），而不是只写"建议完善"。

同时给每条建议标注谈判分级，并附一句可以直接向对方陈述的理由：

- **必改**：不改就不应签署或将直接威胁回款/交付；
- **力争**：显著改善地位，但有让步空间；
- **可让步**：可作为交换筹码。

原因：一份"每条都要改"的报告无法用于谈判。从乙方视角，重点保护验收和回款并设置责任上限；从甲方视角，重点保护成果可用、数据安全、源代码可维护性和替代履行权。不要单方责任最大化，说明哪些上限和例外更可能被对方接受。

## 报告结构

报告是给人读、拿去谈判用的，检查是手段而不是章节。工作流第 2、4、5 步的发现不要各自单独成表——同一事实在四张表里重复出现会把报告切碎。除证据索引外，冲突、缺漏、不对称的发现一律作为风险项进入风险清单总表，并在对应主题的详细分析中展开。

报告标题层级严格使用以下模板（主题小节的名称和数量按合同实际情况调整，其余章节名照用）：

```markdown
# 〈合同名称〉——〈视角〉风险审查与优化报告

## 0. 审查对象与免责声明
## 1. 一页式综合结论
## 2. 证据索引（条款/页码 → 事实 → 风险）
### 2.1 数值与形式自检
## 3. 风险清单总表（按〈视角〉）
## 4. 分主题详细分析
### 4.1 〈主题名〉（R1、R4）
### 4.2 〈主题名〉（R2、R7、R9）
...
## 5. 可直接放入补充协议的优化条文（〈视角〉立场，附谈判分级）
## 6. 签署前/履约中证据清单
## 7. 法律来源与需律师复核事项
## 8. 最终判断与下一步行动
```

模板的硬性约束：

- 风险清单总表给每条风险赋编号 R1、R2…，字段为：编号、优先级、条款/页码、事实、对指定方的后果、建议动作；
- 每个分主题小节标题括号内标注所覆盖的风险编号，全文交叉引用一致、无悬空编号；
- 冲突、缺漏、不对称、行业合规的发现放进风险总表和对应主题小节内展开，**不设**"冲突表""缺失条款清单""不对称清单"等独立章节；附件缺失等形式问题在 2.1 小节记录核对结果、在风险总表中作为风险项出现；
- 优化条文逐条附谈判分级（必改/力争/可让步）和一句可向对方陈述的理由。报告使用简体中文，保留英文技术标识、合同原文术语、命令和文件路径。金额和日期同时保留原文和核对结果，发现矛盾明确列出。

## HTML 交付

同时生成 Markdown 和 HTML。HTML 使用中文字体、适合屏幕阅读和 A4 打印的 CSS，表格支持横向滚动，法律来源保留超链接。用户可见文件保存到当前任务约定的 `outputs/` 目录，文件名包含视角，例如：

`合同名称-甲方视角风险审查与优化报告.html`

使用本技能目录下的渲染脚本（以本 SKILL.md 所在目录为基准的相对路径），避免手写 HTML 造成表格或链接丢失：

```bash
python3 <本技能目录>/scripts/render_report.py \
  --input outputs/report.md \
  --output outputs/report.html \
  --title "合同风险审查与优化报告"
```

脚本优先使用 `pandoc`；缺少 pandoc 时自动降级为内置 Python 渲染，无需手工处理。任何情况下都保留 Markdown 原稿。

**若环境里没有 `python3`**（macOS 12.3+ 已不再自带），跳过 HTML 这一步，直接交付 Markdown 原稿——它本身就是完整的报告，HTML 只是便于打印与分享的附加形态。此时在最终回复里说明未生成 HTML 及原因，不要因为渲染不了就中断整个审查。

## 完成前验证

- 复核第 2 步的全部算术结果（金额、比例合计、税额），至少抽查 3 个金额/日期回到原始页面图像核对；
- 核对风险编号在总表与分主题分析间交叉引用一致，无悬空编号；
- 重新读取 HTML，确认标题、证据索引、风险总表、优化条文、法律链接和最终结论存在；
- 检查 HTML 为 UTF-8、文件非空、链接未截断；
- 最终回复链接到真实路径，说明已生成的文件和最重要的 3 条风险结论。
