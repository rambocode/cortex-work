# 公司知识库

知识库是公司内部资料的唯一可信来源。本技能的目标只有一个：**让回答建立在真实检索到的原文上，并且不浪费上下文**。

## 工具从哪来（重要）

**本技能不写死任何工具名。** 知识库由用户自己接入，服务端可能是自家的，也可能是第三方 wiki，工具叫什么由对方决定。

Cortex 会在系统提示里注入一个 `<company_knowledge_base>` 块，列出**本会话实际可用**的工具，并给每个工具标注角色：

| 角色 | 干什么 |
| --- | --- |
| `search` | 语义检索，返回命中片段与文档坐标 |
| `read` | 按坐标读取文档正文 |
| `list` | 列出知识库里有哪些文档 |
| `ask` | 服务端跑完整 RAG，直接给结论 |
| `write` | 写入沉淀 |

**以那个块为准**。下文说「检索工具」就是指标了 `[search]` 的那个，以此类推。

## 前提检查

先确认系统提示里有 `<company_knowledge_base>` 块、且其中有 `[search]` 角色的工具。

没有就说明当前会话没挂知识库——直接告诉用户「本会话未接入公司知识库，请在 设置 → 知识库 中配置后重开会话」，然后按普通方式回答，**不要假装查过**。

块里没有 `[write]` 角色，说明当前是只读接入。用户要求沉淀时如实说明，别声称已写入。

## 检索的正确顺序

### 1. 先用检索工具，永远从这里开始

一次调用就够。有 `topK` / `limit` 之类的条数参数时用默认值，绝大多数问题不需要调大；问题很宽泛时才提到 15–20。

读返回结果时：

- 命中片段（`preview` 或同义字段）**不是文档全文**，够判断相关性但通常不够回答问题。
- 有相似度分数（`score`）时，同一次检索内比较才有意义：最高分和次高分拉开明显差距时，通常只有第一篇真正相关。**没有分数字段**可能说明服务端本次是关键词匹配而非语义检索，此时结果可能不全，要在回答里说明这一点。
- 结果里的文档坐标（自家知识库是 `sourceId` + `relPath`，第三方可能叫 `knowledgeBaseId` + `documentPath` 等）是后续所有操作的依据，**原样保留、不要改写**。

如果一次检索没命中，换**说法**再试一次（换同义词、换更具体的业务名词、去掉修饰语），而不是反复用同一句话重试。两三次仍无结果就停下来告诉用户「知识库里没有找到相关资料」——这是一个有价值的结论，不要用通用知识填补然后让用户以为是公司规定。

### 2. 需要上下文时才用读取工具，而且要定点读

这是最容易浪费上下文的地方，注意两条：

**只读真正需要的那几篇。** 检索回来 8 条不等于要读 8 篇。先看命中片段判断，通常读 1–3 篇最相关的就够回答。不要"为了全面"把每篇都读一遍。

**能定点就不要从头翻页。** 读取工具若有 `around` 之类的定位参数，把该条命中的片段开头一段原样传进去，就能直接读到命中位置附近。只有确实需要通读整篇（比如用户要求总结整份制度）时，才用 `offset` / `limit` 顺序翻页；返回里 `hasMore=true` 且确实还需要后文，才按提示的 `offset` 续读。

PDF、Word、PPT、Excel 返回的是索引时抽取的文本，排版会丢失，表格可能变形——引用其中的数字前留意这一点。

### 3. 问答工具只在特定情况下用

它会跑一次完整 RAG（检索 + 大模型作答），**耗时数秒到数十秒**，比检索慢一个数量级。

- 该用：用户要的就是一句直接结论，且你不需要看原文细节。
- 不该用：你打算自己读原文再判断（那就用检索）；你已经检索拿到资料了（不要再问一遍）；你想靠它"验证"自己的结论（它和你看的是同一批资料）。

它明确表示答不出来时（如 `unanswered=true`），把这一点如实转达，不要拿它的措辞当事实。

### 4. 列表工具用于摸清范围

只在用户问「知识库里都有些什么」，或你需要确认某类资料是否存在时用。已经知道要查什么就直接检索，列目录既慢又占上下文。

## 回答的要求

### 引用格式以注入块为准（重要）

**每一条来自知识库的结论都要能追溯到具体文档。**

`<company_knowledge_base>` 块里会写明本会话该用哪种引用方式：

- **块里给了 `kb://` 链接格式** —— 就必须按它给的参数名写成可点击链接：

  ```
  [差旅与报销制度](kb://synced_dir-docs-20260101/finance-policy.txt)
  ```

  两段的值直接取检索结果里对应的字段，原样填入，不要改写或猜测。
  **路径里的空格必须写成 `%20`**（知识库文件名带空格很常见）。Markdown 的链接地址不允许出现空格，写了空格整条链接就不成立，用户会直接看到一行原始的 `kb://` 文本。只编码空格，中文、斜杠都保持原样：

  ```
  ✅ [DX0B511 采集与上报链路.md](kb://synced_dir-硬件-20260612/DX0B511/开发/DX0B511%20采集与上报链路.md)
  ❌ [DX0B511 采集与上报链路.md](kb://synced_dir-硬件-20260612/DX0B511/开发/DX0B511 采集与上报链路.md)
  ```

  方括号里的显示名不受此限制，照常写带空格的文件名。Cortex 会把这种链接渲染成可点击的引用，用户点一下就能在侧栏读到原文。

- **块里说不要输出 `kb://` 链接** —— 说明当前服务端没有可用的读取工具，链接点开只会报错。此时**就近写出文件名**即可，不要编造链接。

在正文里就近引用，不要只在结尾堆一个「参考资料」列表：用户读到某句话时就想知道它出自哪儿。同一篇文档在一段话里出现多次时，只在第一次出现处标注即可。

严格区分三类内容，不要混在一起：

- 知识库原文写明的 —— 可以直接陈述。
- 你从多处原文推断的 —— 说明这是推断，并给出依据的文档。
- 知识库里没有的 —— 明确说没查到。如果你补充了通用知识或个人建议，必须标出「以下不是公司资料」。

发现多份文档互相矛盾时（常见于新旧版本并存），**不要自行挑一个当答案**。把冲突摆出来，附上各自的文件名与修改时间线索，让用户判断哪份有效。

不要因为检索结果不理想就用通用知识兜底并让它读起来像公司规定——那比答不出来危害大得多。

## 沉淀回知识库

需要 `[write]` 角色的工具（只读接入时块里没有它）。

**写入前必须先向用户确认内容**。知识库是团队共享的，错误信息会误导其他人，而且写进去之后你多半无法修改或删除。

怎么写：

- 只写提炼后的结论：决策与理由、结论与依据、可复用的步骤。**不要粘贴完整会话转录、日志原文或大段文件内容**——远在触到服务端大小上限之前，就已经没人愿意读了。
- 文件名要具体到能被搜到，带上日期和主题，比如 `2026-07 订单超时故障复盘.md`，而不是 `笔记.md` 或 `记录1.md`。
- 正文用 Markdown，开头一句话说明这份文档是什么、什么时候产生的。
- **同名文档可能写入失败**（多数服务端不覆盖已有内容）。遇到这个报错就换一个更具体的名字，不要用同一个名字反复重试。

## 不要做的事

- 不要调用 `<company_knowledge_base>` 块里没有列出的工具——名字是猜不出来的。
- 不要为了"确保全面"把检索到的每篇文档都读全文——这是上下文浪费的主要来源。
- 不要对同一个问题反复用相同措辞重试检索。
- 不要在已经检索拿到资料后再用问答工具问同一件事。
- 不要把知识库内容当作永远正确：它可能过时。涉及金额、期限、审批人这类会变的信息，提示用户核对文档日期。
- 不要在没有检索到依据时编造公司内部信息。
