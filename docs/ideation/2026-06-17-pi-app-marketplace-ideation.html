Grounding Context

一个贯穿全文的关键判断：用户说的「装工具」，pi 的「工具」其实是 extension（registerTool），而扩展当前完全没有分发通道——它是壳里本地代码生成的 0600 JS（固定文件名每次 pi:open 覆写）。只有 skill（<name>/SKILL.md 目录）有分发雏形。只做「skill 市场」会答错题。

Codebase Context

cortex-work 是 Electron + React 的 pnpm/Turbo monorepo（含 Go 后端）。pi 经 bun 编译为自包含二进制启动；buildArgs / buildRpcArgs 恒以 --no-extensions --no-skills 为基线，再用 --skill / -e 显式注入启用集，-a 一次性信任全部。UI 是启用集的唯一真相源。

分发与安装现状：skill 的下载入口 apps/desktop/src/main/skills/download.ts 是一个 throw "第二阶段实现" 的存根，蓝本是 Go 端 importer server/internal/handler/skill.go（多源 clawhub.ai / skills.sh / github、配额 1MiB/file·8MiB/bundle·128 files、binary-skip、validateFilePath 路径安全、clawhub 带 origin 溯源与版本化索引）。扩展/provider 则完全没有 registry / manifest / 分发单元。

UI 与状态现状：PluginManager.tsx 只有 MCP（纯「敬请期待」占位）与 Skill 两个顶 tab；Skill tab 功能完整但只管理本地（扫描/启停/scope/工作区信任/根增删/开目录/创建 SKILL.md），没有任何「发现 / 可安装」界面。PluginSkill 行只有 name/description/dir/scope/enabled/trusted/shadowedBy——无 version / author / source / installedAt / updateAvailable。无 uninstall / update / delete IPC（卸载=手删目录后重扫）。

激活模型：skill/扩展/provider 都是冷启动 flag，不能会话中途生效；改变经 extensionFingerprint 漂移触发 close-and-reopen（switchSession 恢复上下文）——这是当前唯一的「版本应用」机制。app 自身更新 update.ts（electron-updater + GitHub Releases，用户门控、分阶段状态机）是可借鉴的更新范式。

External Context（先例与陷阱）

pi 官方支持 pi install npm:/git: + settings.json 的 packages[]（本仓库团队选择不用，改本地代码生成——值得调和）。Claude Code 插件：git-repo-as-registry、plugin.json + marketplace.json、SHA pinning、官方/社区双层策展。MCP Registry：canonical/discovery/governance 三层分离（DNS root 类比）。VS Code：repository+publisher 双签名、首装信任对话框、密钥扫描。Obsidian：Restricted Mode 默认开 + 自动逐版本扫描 + 公开安全评分卡。反复出现的陷阱：别先建中央服务器、reviewed≠safe、钉到 SHA、可发现性是承重墙、无法沙箱就用显式同意面。

Past Learnings

本仓库的 pi 系列 plan（skill plugin manager 等）已把 PluginManager 作为前身建好；市场本质是「把延迟项做实」。复用既有安装基底、默认不信任、IPC 四层联动（main handler → ipc/types.ts → preload → core/desktop 镜像）、改变须喂 extensionFingerprint、下载落盘要在 /tmp 隔离副本验证、提交前先 spike——均为已沉淀经验。

统一工件描述符 + 多扩展共存布局——让「工具」真正成为可分发单元

轴1 · 索引与分发 Confidence 88% Complexity Low–Med
Description
定义一个 kind-tagged 工件描述符（{kind: skill|extension|provider|mcp, name, version, source, checksum, origin}），让市场的索引、下载、信任、版本逻辑只写一遍并同时服务四类工具；同时把扩展的物理布局从「userData/pi-extensions/<固定名>.js 每次覆写」改为 per-instance 目录，buildRpcArgs 动态收集多个 -e，使多个第三方工具可共存。
Basis
directpi-extensions.ts:36-52,160-167 扩展是写死模板的固定文件名、每次 open 覆写、无 per-instance 状态；evidence-index-distribution.md 确认「扩展今天完全没有 download/marketplace path」。pi-rpc.ts:208-213 多 -e 已支持，仅缺 per-instance 槽位。
Rationale
这是整个市场的地基与最高杠杆点：不先让扩展成为可分发、可共存的单元，市场就只能装 skill（提示词），装不了用户真正想要的 tool——直接违背诉求。一个 kind 标签让后续 version/uninstall/update/provenance 一次覆盖四类。
Downsides
触及 IPC 四层镜像与 extensionFingerprint 组装；per-instance 布局迁移需兼容现有内置扩展；描述符是新契约，定错会拖累后续所有方向（建议先 spike 锁形状）。

调和 pi 原生 pi install / packages[]，而非另起一套安装运行时

轴2 · 安装与激活机制 Confidence 82% Complexity Med（多为 spike/调研）
Description
pi 本身已提供 pi install npm:@foo/bar / pi install git:...@v1 与 settings.json 的 packages[] 清单。市场不必自建下载/依赖/解析栈，而可把 pi 二进制当安装运行时：UI 写 packages[]、安装经 spawn(pi, ["install", ref]) 走 pi 自己的解析器，我们只做策展、信任与 UI 层。这是决定整体架构的战略岔路，应先于其他实现项用一个 spike 拍板。

调和分析：团队当初的「绕开」是否真的禁止借力？

两个被混为一谈的「绕开」其实是不同决策，需要拆开：

  • 绕开 pi 自动发现（--no-extensions --no-skills 基线，pi.ts:57-62 / pi-rpc.ts:201-204）——理由是「UI 为启用集唯一真相源」，与是否用 pi 下载无关：用 pi install 下载后，仍可继续用 --no-skills + 显式 --skill/-e 注入，两者不冲突。
  • 绕开 pi 的 in-process SDK（plan 记录：避免把 pi 的 ESM 闭包 minimatch/typebox/undici 引入 Electron 主进程，正是 bun-binary 决策的同源动机）——但这条只针对「在主进程里 import pi」。
✓ 关键支点（本次核对所得）
pi 是 bun 编译的自包含二进制，把整个依赖闭包 inline、不依赖 node_modules，经 child_process.spawn 执行（pi-locate.ts:2）。因此 spawn(pi, ["install", …]) 在pi 自己的进程里完成解析，与现有的 --mode json/rpc spawn 模型一样进程隔离——主进程从不 import pi 的 ESM。「ESM 依赖地狱」这条理由不适用于 shell 出 pi install。这把 idea 的可行性从「存疑」推向「大概率可借力」。

Spike 设计（bun 本地跑，无需真实 key）

  1. 在 /tmp 隔离目录用 bun 跑 pi 二进制：pi install npm:<一个小公开扩展包> 与 pi install git:github.com/…@<sha>，确认落盘位置、是否写 settings.json packages[]、退出码与错误形态。
  2. 验证共存：装完后以 --no-extensions --no-skills 启动并显式注入，确认 pi 装的包与我们注入的 -e/--skill 不互相覆盖、不触发自动发现。
  3. 验证离线/失败：断网执行 pi install 的降级行为；npm/git 鉴权失败时的可恢复性。
  4. 定位 pi 读取 settings.json 的路径与我们 spawnEnvFor 注入的 env（HOME/工作目录）是否一致——决定 packages[] 落在哪、是否被多 workspace 串场。

决策标准（spike 后二选一）

  • 借力 pi（首选，若 spike 通过）：pi install 可控、落盘可定位、可与显式注入共存、离线失败可恢复 → 市场只写 packages[] + 策展/信任层，省掉整套 importer。
  • 自建（回退）：若 pi install 强制自动发现、把 settings.json 变成与 UI 打架的第二真相源、或离线行为不可接受 → 退回 idea 3 的 Go importer / git-repo 路线。
Basis
external pi 官方 docs/extensions.md：npm/git 包安装 + package.json 的 pi.extensions 字段 + settings.json packages[]。directpi-locate.ts:2 二进制 inline 依赖闭包、spawn 执行；pi.ts:57-62 / pi-rpc.ts:201-204 基线 flag 是「UI 真相源」而非禁下载；pi-rpc.ts:241 env 经 spawnEnvFor 注入。
Rationale
复用上游成熟解析器省掉整套下载/依赖/校验栈，未来 pi 升级 packages 能力可白嫖，正是「别先建中央服务器」陷阱的最优解。深化后的核心结论：团队绕开的是「in-process import」与「自动发现」，二者都不禁止 shell 出 pi install——这个岔路因此值得在写任何 importer 代码之前用半天 spike 解决，避免重复造一套 pi 已有的轮子。
Downsides
pi install 用全系统权限执行任意代码，信任问题不因借力消失（仍须走 idea 5 同意门）；packages[] 是 pi 的 lockfile，与「UI 单一真相源」存在张力——若 pi 装的包也参与自动发现，会形成第二真相源（spike 步骤 2 专门验此）；绑定 pi 的 install 实现细节，pi 版本升级可能改变行为（已 pin 0.79.2 缓解）。

分发后端二选一：复用 Go importer（clawhub/github）vs git-repo-as-registry

轴1 · 索引与分发 Confidence 82% Complexity Med
Description
市场的「源」有两条已验证路线，应明确选型（或分阶段并存）：A) 复用 Go importer——download.ts 存根直接接线到 skill.go 已实现的多源解析（clawhub.ai / skills.sh / github）、配额、binary-skip、路径安全，desktop 经 skills:download IPC 调用，安全逻辑写在 Go 一处、desktop/web/团队侧共享。B) git-repo-as-registry——团队私有源就是一个含 marketplace.json + 各工件目录的 git 仓库，clone/pull 同步、SHA 即版本钉、PR 即策展，零中央服务（沿用 userGlobalRoots 已有的「订阅多个全局根」雏形）。
Basis
directdownload.ts:1-15 桩注释已列全蓝本（多源/配额/二进制/路径安全/frontmatter 复用）；skill.go 的 detectImportSource 已支持 github.com 源并处理限流。external Claude Code 的 git-repo-as-registry + marketplace.json + SHA pin + 双层策展是成熟范式。
Rationale
两条路都已被各自的先例验证过，区别在运维与策展模型：A 复用既有 Go 校验、即接即用、适合官方策展集；B 零后端、天然带版本/审计/PR 评审、适合团队私有源。明确表态（而非含糊地两者都做一半）能让后续所有安装/信任/更新逻辑对齐到一个 source 模型。
Downsides
A 绑定 clawhub/skills.sh 的可用性与格式；B 要求每个用户能访问该 git 源（私有仓库的鉴权）、且大仓库 clone 成本高。二者在「钉 SHA」上一致，但索引刷新与离线行为差异大。

InstalledArtifact 安装账本 + 事务化可回滚更新

轴5 · 生命周期管理 Confidence 85% Complexity Med
Description
在 PiSkillSettings 旁新增一张持久的 installedArtifacts: {id, kind, name, version, sourceUrl, checksum, installedAt, origin}[]。它把今天「只有 enable/disable + trust + root」的薄状态补成真正的安装账本，回答「我装了什么、哪个版本、哪来的、改过没」。在此之上把安装/更新/卸载建模为事务化代际切换：生成新 install-set → extensionFingerprint 漂移触发冷重开切换 → 保留上一代以便一键回滚，更新借 update.ts 的用户门控状态机，checksum 做篡改检测、SHA 做版本钉。
Basis
directevidence-lifecycle.md：PiSkillSettings/PluginSkill 无 version/installedAt/source/checksum，无 delete/update IPC（卸载=手删）；pi-session.ts:18-20,152-162 指纹漂移即关旧重开本质上已是「代际切换」；skill.go:1634-1638 server 已建模 origin{type,source_url,slug} + version。external Claude Code SHA pin；NixOS / Android A-B 的原子升级+回滚。
Rationale
没有安装账本，市场只是一次性下载器：无法管理、更新、溯源，供应链事故时连「哪些机器装了恶意版本」都查不出。复用 server 已验证的 origin/version 模型 + pi 已有的冷重开机制，一次补齐整个生命周期轴，而非散落补一堆 IPC。
Downsides
保留「上一代」需要额外磁盘与目录管理；checksum 校验要在重开前介入注入门；与 idea 1 的描述符强耦合（version/checksum 字段须先在描述符里存在）。

安装信任体系：同意面 + origin 分层授信 + 落「默认管制专区」（并修一个计划漏洞）

轴4 · 信任与安全 Confidence 84% Complexity Med
⚑ 顺带捕获的计划漏洞
现行 download.ts 计划把市场内容落到 userSkillsRoot()，而该根在 skillsRoots() 里被当作默认信任的 global 源（types.ts:412-418）——按此规划，「从互联网装的代码会自动可信」，绕过了已声明的命名威胁模型。市场上线前必须纠正落地分区。
Description
三件互锁的事：(1) 安装即同意面——点安装不静默落盘，先弹一张卡展示 origin / source_url / checksum / 声明的工具权限，确认后才写盘并加入启用集（VS Code/Obsidian 范式）。(2) origin 分层自动授信——内置与官方策展源自动信任，陌生 github / workspace 默认不信任、首装弹一次并记住该来源，把「逐 skill 手点」降为「按来源一次决策」。(3) 落默认管制专区——纠正上面的漏洞，市场内容落一个默认不信任的专用根而非自动信任的 global 根。可选叠加：新装工具首启先在抛弃式「影子会话」跑探针，行为干净再正式加入信任集。
Basis
directtypes.ts:394-396 命名威胁「恶意仓库经 .cortex-desktop/skills + -a 任意代码执行」；pi.ts:67 / pi-rpc.ts:209-213 一个 -a 一次信任全部；types.ts:412-418 global 根恒 trusted、download.ts:28 落 userSkillsRoot()（即漏洞）。external VS Code 首装信任对话框、Obsidian Restricted Mode 默认开。
Rationale
市场把「任意第三方可执行 JS 默认信任」常态化，是把现有 workspace-skill 威胁放大到全网。无法真正沙箱时，显式同意面 + 按来源分层 + 正确的落地分区是唯一现实防线；reviewed≠safe，所以信任决策必须在安装这一刻被人显式做出。
Downsides
同意面会增加安装摩擦（需在「零摩擦」与「安全」间调参，分层授信正是为此）；影子会话探针是额外构建且只能抓显式越权、抓不住潜伏逻辑；分区纠正需改动 skillsRoots() 的信任派生，影响面需回归测试。

工作区内联市场——zero-remote MVP，信任即安装

轴3 · 浏览与发现 UI Confidence 78% Complexity Low
Description
「安装=从远程下载」是个假设。一个 git 仓库里的 .cortex-desktop/skills 已经是一组随项目分发的工具，只是默认不可信。把它升格为「项目内联市场」：PluginManager 给工作区 skill 一个明确的「评审并信任」流——展示 frontmatter / 文件清单 diff，信任即安装。零下载、零远程目录、零新后端，却已经让团队成员互相分发工具。可作为市场的第一个可发布形态，用来在不引入远程分发风险的前提下打通发现→信任→激活的端到端链路。
Basis
directtypes.ts:394-396 工作区 skill 默认禁用需显式授信（威胁模型已就位）；PluginManager.tsx:447-486 工作区卡已有「信任并启用」动作，只缺一个让人敢按下的评审界面。
Rationale
团队协作的核心场景里工具天然随 repo 走。把既有威胁面反转成分发渠道，无需任何远程基础设施即可上线一个真实可用的市场雏形，并正面回应「reviewed≠safe」——评审入口就在信任之前。是验证整套信任/激活机制的最低风险切入点。
Downsides
仅覆盖「项目内已有」的工具，不解决跨项目发现；评审界面要呈现足够信息让用户判断（否则又退回盲信）；与远程市场（idea 3）最终需统一到同一安装/信任管线，避免两套实现。
7

agent-native 自助安装——pi 缺能力时经同意面主动请求装工具

轴2/3 · 安装激活 + 发现 Confidence 72% Complexity Med
Description
反转发现方向：不让用户去逛货架，而把市场暴露为 pi 能调用的能力。当 pi 在一轮里发现缺某能力（反复声明做不到、或命中不存在的工具名），经现成的 askquestion 同意通道向用户请求：「市场里有 X 可以做这个，装吗？」用户一键批准 → 后台下载落地 → extensionFingerprint 漂移自动重开 → 下轮即生效。安装恰好发生在需要的时刻，可发现性从用户负担转为 agent 职责。
Basis
directpi-extensions.ts:41-48,183 生成扩展即 pi.registerTool，askquestion 是已落地的同意通道；messages.ts:961-986 注入门是单点，可挂「能力缺口探针」。reasoned 缺口探测逻辑需新增，但激活与同意两环已现成。
Rationale
这是最贴合本产品 agent-native 理念（CLAUDE.md 强调「用户能做的 agent 也能做」）的方向，且复用团队刚做完的 askquestion 同意面。把「可发现性承重墙」从一个需要建造的浏览 UI，部分转移到 agent 推理上——零浏览成本的安装。
Downsides
缺口探测易误报/滥推荐，需要克制的触发阈值与「不再提示」开关；让 agent 触发安装放大了信任面，必须严格走 idea 5 的同意门；依赖目录与下载链路（idea 1/3）先就位才有意义。

Rejection Summary

#候选剔除理由
R1独立「发现」第三 tab（远程目录 UI）重复——合并入 #3/#6，它只是安装后端的 UI 面，无独立决策价值
R2创作-发布闭环（闪记深化/ce-skill → 发布到市场）过早——是反向（分发而非消费）流，须等目录分发先存在
