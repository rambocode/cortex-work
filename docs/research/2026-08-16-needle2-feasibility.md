# Needle 2 小模型可行性验证报告

日期：2026-08-16 · 结论：**当前形态 no-go（中文场景全线不达标）**；唯一可能的翻盘路径是官方 `needle finetune` 做中文领域微调，属后续选项。

> 追加约束（同日）：**模型大小 ≤ 20MB**。续篇调研见文末「二、≤20MB 约束下的替代方案」——结论：路由/工具选择改用非生成式轻量分类器（模型 31–47KB，实测 90–100%），标题生成在该约束下无可行生成模型。

## 被验证对象

[Cactus Compute Needle 2](https://cactuscompute.com/needle)（[HF](https://huggingface.co/Cactus-Compute/needle2)，MIT）：45M 参数、14MB 权重、2-bit 量化训练、256 token 滑动窗口。**只做工具调用与 schema 结构化抽取，无自由文本生成**；官方生态为 Python SDK（`cactus-needle` 2.0.3）+ 简易 CLI，无 Node 绑定。

实验环境：本机 Apple Silicon macOS，Python 3.14 venv，SDK 直调。脚本与原始结果（可复跑）：scratchpad `needle2-spike/`（`exp_a_routing.py` / `exp_b_title.py` / `exp_c_tools.py` / `exp_d_english_control.py`，结果落盘 `results/*.json`）。

## 结果总览

| 实验 | 场景 | 结果 | 判定 |
|---|---|---|---|
| A 路由分类 | 复刻 `voice-intent/understand.ts` 的 5 意图，30 条中文 | **准确率 46.7%**（判对的几乎全是空调用兜底出的 continue_chat；13 条明确控制命令仅 0 条判对，另有 4 条无关句被误判成 `disable_screen_context` 假阳性） | ❌ |
| B 标题生成 | 单工具 `set_title`，20 条中文首条消息 | 表面格式合格 15/20，**但全部是照抄输入开头到第一个标点，零概括**，且丢字（「机器学习」→「机器学书」、「年终总结」→「年结」）；2 条直接空输出 | ❌ 不如现行非 LLM 的 16 字截断兜底 |
| C 带参工具调用 | 5 个带参工具，20 条中文指令 | **选对工具 5/20**，大量指令被兜底扔进 `search_files`；参数抽取丢字（「给妈妈打电话」→「提醒我电话」）；**实测产出非法 UTF-8 字节导致 SDK `json.loads` 崩溃**（`UnicodeDecodeError`，exp_c 首轮） | ❌ |
| D 英文对照 | 同套工具换英文输入 | 路由 6/10、工具选择 4/8 | ⚠️ 明显好于中文但仍不稳 |
| 性能 | 冒烟 + 各实验延迟 | 冷启动首次 8s（含下载权重），热启动 **40ms**；单次调用 P50 34–82ms；常驻内存 **47MB**（Python 进程 RSS）；~1300–1800 tok/s 解码 | ✅ 工程指标属实且惊艳 |

## 结论拆解

1. **性能叙事成立，能力叙事（对我们）不成立。** 延迟/内存/体积确实是「本地路由器」的理想数字——如果它答对的话。
2. **中文是硬伤，且有两层：**
   - 语义层：中文控制命令几乎无法映射到正确工具（英文对照证明是语言问题而非任务设计问题）；
   - 字节层：2-bit 量化 + 逐字节生成中文时会产出**非法 UTF-8 序列**，这不是 prompt 能修的。
3. **标题生成天生出界。** 模型无自由文本能力，「标题」退化成输入前缀截断 + 随机丢字。现行 `applyFallbackTitle`（`packages/core/personal/messages.ts:3473`，首条消息截 16 字）做同样的事且零成本、零错字。
4. **英文场景也未到可用线。** 6/10 的路由准确率低于 `understand.ts` 现行方案对小云端模型的实际要求（现网走 `postChatCompletion` + 温度 0，失败静默兜底，可容忍偶发错，但 40% 错误率不可容忍）。
5. **方法论备注（复跑必读）：** Needle 引擎是进程级共享且有状态的，连续 `complete()` 会互相污染（实测置信度单调衰减、全部退化成空调用）——评测必须逐样本 `reset()`。`confidence` 字段波动极大（0.0006–0.9999）且与正确性弱相关，不能当路由阈值用。

## 建议

- **路由/小任务不引入 Needle 2。** 想给标题生成减重，正确的低成本改动是把 `autoTitle` 从 `cli:oneshot` 重链（spawn claude CLI、60s 超时）改挂 **Model Gateway `postChatCompletion`** + 云端小模型（走 `automaticRoles.title` 已有配置位），与语音意图分类同构——这是另案，不在本次范围。
- **若坚持端侧小模型方向**，两个后续选项按优先级：
  1. `needle finetune` 用中文路由语料微调（官方支持，LoRA 级成本；但字节层 UTF-8 问题未必可微调修复，需先小样本验证）；
  2. 换 0.5B–1.5B 级多语言小模型（如 Qwen 系）走 llama.cpp/MLX 本地推理——体积和内存上一个量级，但中文能力有基本盘。
- 集成形态备忘（若未来任何端侧模型 go）：官方无 Node 绑定，现实路径是主进程 spawn Python/HTTP server 子进程，或按其 ctypes 动态库（SDK 内 `_lib()` 加载 `.so/.dylib`）做 N-API 绑定；挂点建议 `automaticRoles` 小模型分档 + `voice-intent` 的 `intentModelRef`。

## 数据溯源

每个数字对应 `needle2-spike/results/` 下同名 JSON（逐样本记录输入/期望/实际/置信度/延迟/异常）。样本标注依据 `understand.ts` SYSTEM_PROMPT 的边界规则与 `chat.json:230` autoTitlePrompt 的格式要求。

# 二、≤20MB 约束下的替代方案（续篇）

## 约束对候选池的影响

原定复测名单 Qwen3-0.6B（Q8 约 640MB / Q4 约 400MB）、LFM2-700M（Q4 约 400MB）、Gemma-3-270M（约 170MB）**全部超限出局**。行业现状（2026-08）：通用小模型的实用下限在 270M 参数（打包 150MB+）以上；**≤20MB 的生成式模型生态位只有 Needle 系**（Cactus HF org 无多语言变体；`needle-pebble-ft` 证明官方微调路线真实可用）。

推论：20MB 内做「路由/工具选择」的正确技术不是生成式 LLM，而是**任务专用分类器**。已实测验证（同一套评测集，与 Needle 2 数字直接可比）：

## 实测结果（实验 E / F，脚本与结果同目录）

| 方案 | 任务 | 结果 | 模型大小 | 单次延迟 |
|---|---|---|---|---|
| char 1-3gram TF-IDF + LinearSVC（校准概率 + 低置信兜底） | 路由 5 意图，30 条评测 | **27/30（90%）**，命令 13/13 全对，失误全在疑问/复合句陷阱 | **47KB** | 0.94ms |
| 同上 + 产线同款疑问句/复合句否决规则（`isFastPathVetoed` 思路） | 同上 | **30/30** | 47KB + 一条正则 | ~1ms |
| 同技术训练工具选择 5 分类 | exp_c 同款 20 条 | **20/20** | **31KB** | 0.69ms |

训练数据为人工合成语料（116 / 75 条，与评测集严格不重合），训练耗时 0.02s——意味着**新增意图/工具只需加十几条例句重训**，无部署成本。

**诚实标注**：评测集小且否决正则是照着已知陷阱形态写的，30/30 有对小样本过拟合之嫌。数字证明的是「该路线能到可用区间」，不是产线保证；上线前必须用真实语音日志做保留集评测。

## ≤20MB 约束下的分任务结论

| 任务 | 判定 | 方案 |
|---|---|---|
| 路由/意图分类 | ✅ go | 规则否决 + 轻量分类器（KB 级）；语义要求提高时升级 **ALBERT-tiny-zh 微调**（4M 参数，约 16MB，仍在限内） |
| 工具**选择** | ✅ go | 同上 |
| 工具**参数抽取** | ⚠️ 窄可行 | 分类器选工具 + 每工具规则/正则抽参（时间表达、`叫/包含/关于` 后接实体）对窄 schema 可行；通用自由参数抽取需要生成能力，20MB 内无解 |
| 会话标题生成 | ❌ no-go | 20MB 内不存在可用的中文生成模型。保留现行 16 字截断兜底（`applyFallbackTitle`），或走云端小模型（Gateway 路线，不占本地体积预算） |
| 生成式兜底 | ⚠️ 唯一选项 | `needle finetune` 中文语料微调（官方路线），但字节层 UTF-8 缺陷未必可修，需先小样本验证再投入 |

## 集成备忘

- 分类器方案天然适合 Electron：模型 KB 级可直接打进 asar，主进程毫秒级同步推理，无子进程、无 Python 依赖（上线实现可用 TS 重写 TF-IDF + 线性权重导出，或 ONNX Runtime）。
- 挂点与原报告一致：`voice-intent` 现有「精确命令 → 拼音模糊 → LLM」三级流水线里，分类器可作为第 2.5 级插入，LLM 仍作兜底——正是产线现有架构的自然延伸，而非替换。
